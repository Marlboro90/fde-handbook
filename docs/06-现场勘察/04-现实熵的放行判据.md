前三节给了三样工具：分级、三条路、变形清单。这一节讲怎么判断现实层收敛了。

判据不是「勘察报告写完了」，也不是「数据源清单齐了」。判据是：**你写的那份记录，能预测进场后第三天会出什么事。**

这个标准有点怪，但它可检验——而且它是唯一能区分「勘察」和「参观」的标准。

## 现场

锦程精工 A 项目，第一次勘察花了三天。产出是一份 40 页的报告：23 张表的结构、18 个数据源、系统架构图、网络拓扑、权限清单。

交给客户，客户说「很详细」。交给项目经理，他问了三个问题：

- 「第一周会不会卡？」——「应该不会吧。」
- 「哪个环节最可能拖时间？」——「看情况。」
- 「如果只做一类工单，够不够数据？」——「要查一下。」

三个问题都答不上来。报告里有 40 页事实，但没有一个判断。

这份勘察的成本是三天人力，产出是三天的信息搬运。**它没有降低任何不确定性，只是把不确定性描述得更详细了。**

## 预测的三类内容

有效的勘察记录，必须能预测三件事。每一件都具体到可以事后核对。

**第一类：会缺什么。**

不是「数据可能不全」，是「设备台账里 2019 年前入厂的设备，有 40% 没有对应的型号编码，这部分设备无法自动匹配故障知识」。

预测的写法要带数字和范围：「比例大概在 30%–50%，依据是抽了 100 条看到 43 条缺」。

进场第三天核对：是三成还是五成？如果完全不在范围里，说明抽样有偏，或者你问错了人。

**第二类：会吵什么。**

不是「可能有分歧」，是「业务方和信息部门会在『用哪份工单数据』上产生分歧，因为两边的口径不同」。

这一类的预测最难，因为它涉及人。但它最有价值——因为它决定了你能不能提前准备对账材料。

判断依据通常来自一个细节：两边的人是否用过同一个词指代不同的东西。比如「故障工单」，业务方指的是客户报修的，信息部门指的是工程师填的，两者数量差三倍。

**第三类：会卡多久。**

不是「接入可能有延迟」，是「SaaS 那个源要等厂商开通 API，按以往经验 2–3 周，因此第二个迭代的前半段只能用一个源」。

这一条直接决定排期。而且它有明确的验证点：进场第一周结束时，那个 API 开通了没有？

## 勘察记录的最小字段

不需要 40 页。八个字段，两页足够。

| 字段 | 内容 | 为什么必须有 |
| --- | --- | --- |
| 源清单与级别 | 每个源 + A/B/C/D 级 + 依据 | 决定方案能用什么 |
| 权限与签字人 | 每个源谁签、周期多久 | 决定工期量级 |
| 通道验证结果 | 已跑通 / 未验证 / 不可行 | 区分「理论上」和「事实上」 |
| 缺口清单 | 缺什么、比例多少、怎么补 | 决定补救工期 |
| 分歧点 | 谁会吵、吵什么、依据是什么 | 决定要不要提前对账 |
| 卡点预测 | 哪个环节会卡、卡多久 | 决定排期缓冲放哪 |
| 三天预测 | 进场第三天会出什么事 | 勘察是否有效的判据 |
| 复核时间 | 什么时候回来核对预测 | 让预测可被证伪 |

最后两行是这份表和普通勘察报告的分水岭。**没有预测，就没有判据；没有复核时间，预测就无法被证伪。**

## 用一次勘察调整排期

勘察的价值最终体现在排期上。三个动作：

**动作一：把卡点前置。**预测到「SaaS 要等两周」，就把这个源的依赖功能排到第二个迭代，第一个迭代只用已通的源。

**动作二：给缺口留缓冲。**「40% 缺编码」意味着要补映射，这是 3–5 天。这个时间必须出现在计划里，而不是「到时候看」。

**动作三：把分歧点变成会议议题。**预测到业务方和信息部门会吵口径，就在第一周安排一次对账会，让双方当场把口径定下来。这比等到第三周发现数据对不上要省得多。

三个动作的共同点：**勘察不是收集信息，是重新安排工作。**

## 什么时候勘察算做完了

三条同时满足：

1. 你能对「第三天会出什么事」给出三个具体预测，每个都带数字或时间；
2. 每个预测都有复核时间点；
3. 排期因为这些预测改过至少一处。

第三条最容易被跳过，也最能说明问题。如果勘察之后排期一个字没改，那这次勘察要么没发现任何问题（罕见），要么你发现了但没当真。

还有一个更隐蔽的情况：排期改了，但改的是「加缓冲」而不是「调结构」。给每个环节都加三天缓冲，看起来是尊重不确定性，实际上是把判断责任推给了时间。真正有用的调整是结构性的——把依赖未通源的功能往后挪、把分歧点提前开会、把补映射单独立项。

## 判据卡

| 判据项 | 合格线 | 不合格信号 | 处置 |
| --- | --- | --- | --- |
| 有三天预测 | 三个具体预测，带数字或时间 | 只有「可能有一些问题」 | 重写，落到可核对的粒度 |
| 预测可证伪 | 每个预测都有复核时间点 | 写完就归档 | 在日历上加核对项 |
| 排期已改 | 至少一处排期因勘察结果调整 | 排期与勘察前一致 | 说明勘察没被使用，重做判断 |
| 通道已验证 | 至少一个源真实取到过数据 | 全是文档结论 | 要一次真实导出 |
| 分歧点已识 | 能说出至少一处口径分歧 | 认为「客户内部很统一」 | 分别问业务方和信息部门同一个问题 |
| 缺口有数字 | 缺口带比例与抽样依据 | 只有「部分缺失」 | 补抽样，给出区间 |

第三行是这一节的核心判据。**勘察有没有用，看排期有没有变。**

## 动手练习

**第一题（改写）**

把下面这句勘察结论改写成可证伪的预测：

> 「部分老设备的型号信息可能不完整，需要进一步确认。」

**第二题（找漏）**

一个团队做完勘察，报告很详细，排期也调整了。进场后第一周顺利，第二周突然发现「所有工单的时间字段都是空的」。这个勘察缺了哪一环？

## 参考答案

**第一题**

改写示例：

> 「2019 年前入厂的设备（约占台账 35%），型号编码字段为空或不规范的比例预计在 30%–50% 之间。依据：随机抽 100 条，43 条缺失或格式不符。影响：这部分设备无法自动匹配故障知识，需补一张映射表，预计 4 个工作日。复核时间：进场第 3 天，用全量数据核一遍实际比例。」

四个要素：范围（2019 年前）、比例（30%–50%）、依据（抽样 100 条）、复核时间。少任何一个都不可证伪。

**第二题**

缺的是「通道验证」这一环里的**字段级验证**。

他们验证了「能取到数据」，但没验证「取到的数据里有没有关键字段」。时间字段为空，说明要么源系统本来就不记，要么导出时被丢了，要么字段名不同。

正确做法：通道打通后，第一件事不是拉行数，是**拉一条完整记录，逐字段核对**——特别是时间、状态、关联 ID 这三类，因为它们决定后续能不能做关联分析。

这也说明为什么「通道已验证」这一栏要写「已跑通 / 未验证 / 不可行」三态，而不是简单的「是/否」。「能连上但字段缺」属于中间态，需要单独标注。

## 自检清单

- [ ] 我的勘察记录里有三个带数字或时间的预测
- [ ] 每个预测都有复核时间点
- [ ] 排期因勘察结果改过至少一处
- [ ] 至少一个源我真实取到过数据，且逐字段核对过
- [ ] 我能说出至少一处业务方与信息部门的口径分歧
- [ ] 缺口清单带比例与抽样依据

> 本节为原创论述。
>
> 关于主张的边界：第二次进同一个客户现场时，勘察可以大幅简化——因为历史记录就是你的预测基线。但要注意一个陷阱：**上次的结论可能已经过期**。系统升级、人员变动、流程调整都会让旧预测失效。简化的是勘察动作，不是复核动作；每次进场仍要核对一遍「三件事有没有变」。
