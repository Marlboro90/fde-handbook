进场之后，第二个决定是「怎么把数据弄出来」。

多数人的直觉是：新系统好接，老系统难接。这个直觉在真实项目里经常反过来——一个跑了二十年的老系统可能三个小时就打通了，一个去年上线的 SaaS 折腾了六周还没拿到数据。上一节把数据按可信度分了四级，也分了能拿来干什么。这一节讲，在「能拿来干什么」和「真能弄出来」之间，还隔着一道写权限——它往往比技术难度更决定进度。

差别不在技术年代，在**写权限在谁手里**。

## 现场

锦程精工 A 项目，需要接三个源。

**第一个：2004 年就上线的主机系统**，跑在一台没人愿意碰的机器上，界面是字符终端。团队预计最难。结果第一天就通了——因为客户有一位 DBA 认识这个系统，他有只读账号，一条命令就能把需要的表导成 CSV，每天早上自动跑一次。

**第二个：去年买的 SaaS 客服系统。**界面漂亮，有 API 文档。团队预计最容易。结果六周没通——API 只对「企业版」开放，客户买的是标准版；数据导出功能有，但要厂商工单审批，一次审批五个工作日；想直连数据库，厂商说「不提供」。

**第三个：集团下发的报表平台。**有接口，也有权限，但权限归集团信息中心管。客户自己申请了三次，每次都被打回，理由是「需说明用途并承诺不二次分发」。

三个系统的接入工作量，与它们的年龄完全无关。**只跟一件事有关：谁能签那个字。**

## 三条路，各自的真实代价

**第一条：有接口。**

前置条件不是「有 API 文档」，是「你有这个接口的调用权限」，而且额度够用。

真实耗时：如果权限现成，一条链路一到三天；如果需要申请，按周算，而且不可控。

失败模式：文档写的字段和实际返回的不一致；分页有隐藏上限；限流比文档写的严格；沙箱环境和生产环境行为不同。

**第二条：没接口，但有数据库或文件通道。**

三条子路，按可靠性排序：

- **数据库只读账号**——最稳。需要 DBA 配合，且要确认只读账号不会被审计拦；
- **定时导出文件**——次稳。需要客户 IT 配一个定时任务，落地到你们都能访问的目录；
- **界面自动化**——最不稳，但在前两条都不通时是唯一选择。用浏览器自动化模拟人工操作，从没有接口的老系统里取数。

界面自动化的边界要写清楚：它能应付「表单固定、流程不变」的系统；一旦对方改版、加验证码、加二次确认，它就断。所以它适合做**一次性取数**或**低频同步**，不适合做实时链路。

**第三条：不许碰。**

客户明确说数据不能出某个边界。这不属于「接入方式」，属于下一节要讲的交付形态变形。

## 判断顺序：先问权限，再问技术

进场第一小时该问的，不是「你们有什么系统」，是四个问题：

1. **这个系统的写权限（或管理员权限）在谁手里？**是客户自己的 IT，还是厂商，还是上级单位？
2. **拿到只读权限需要谁签字？**签字的周期大概多久？
3. **有没有现成的导出通道？**哪怕是手工导出，先确认「能导出来」。
4. **导出有没有格式或字段限制？**很多系统导出会丢字段、丢历史。

四个问题的答案，直接决定这一路的工期量级。技术细节可以后面再谈。

一个实用判断：**如果答案是「要问厂商」，工期至少按两周起算**，因为中间有一次商务沟通。如果是「要问集团」，按一个月起算。

## 权限之外的两个隐形门槛

**网络策略。**数据能导出来，不代表你的机器能连上去。客户的网络通常分区分域，开发机在办公网、数据库在生产网，中间隔着防火墙和审批。这一项经常比权限更耗时，因为它涉及两个部门的会签。

判断方法：进客户现场第一天，就让对方给你开一台能同时访问「你需要的源系统」和「外网」的机器。如果开不出来，先解决这件事，别急着写代码。

**审计。**金融、医疗类客户会对数据访问做审计留痕。这意味着：你的每一次查询都可能被记录并事后检查。这不影响可行性，但影响你的取数方式——不能随手 `select *`，要写清用途、限定字段、避免拉全表。

## 一个反直觉的做法：先接最脏的那个

团队通常按「重要性」排序接入顺序，先接最关键的源。

更有效的顺序是**先接最不确定的那个**——那个你还没搞清权限归属、还没验证过能否导出的源。

理由：接入的不确定性远大于工作量。关键源如果技术路径清楚，两小时能通；不确定的源可能卡三周。先做不确定的，能最早暴露排期风险；先做确定的，会让你在第三周才发现有个源根本拿不到。

## 判据卡

| 判据项 | 合格线 | 不合格信号 | 处置 |
| --- | --- | --- | --- |
| 权限归属清楚 | 每个源都能说出「谁签字、周期多久」 | 只知道「他们有系统」 | 逐源问，写下签字人与周期 |
| 通道已验证 | 至少跑通一次真实取数，不是「理论上可以」 | 只有接口文档或口头承诺 | 要一次真实导出，哪怕手工 |
| 网络已打通 | 有一台机器能同时访问源系统与外网 | 还没试过 | 第一天解决，别拖到开发阶段 |
| 顺序按不确定性排 | 最不确定的源最先接 | 按重要性排序 | 调整顺序，先探路 |
| 有备用路径 | 每个源至少有两条可行路径 | 单点依赖一个接口 | 补备用，界面自动化也算 |

第二行是硬要求。**「理论上能接」和「已经接通过一次」之间，差着整个项目的排期准确性。**哪怕手工导一份出来，也比看文档可靠。

## 动手练习

**第一题（判断）**

三个源，你只有两周接入时间。按不确定性排序，说明理由：

- A. 客户自己的 MySQL，IT 部门直接管，已确认有只读账号。
- B. 厂商提供的 REST API，需要客户走商务流程开通。
- C. 一台 2010 年的 Windows 服务器上的 SQL Server，没人知道密码，但机器还在跑。

**第二题（找漏）**

一个团队花三周接一个 SaaS 系统的 API，最后失败。复盘时发现所有技术工作都做对了。他们最可能漏了什么？

## 参考答案

**第一题**

顺序：**B → C → A**，按不确定性从高到低。

- B 的不确定性最高：技术上是通的（有 API），但「走商务流程」这件事周期不可控，可能三天，也可能一个月。它应该第一个启动，因为它是唯一可能推翻排期的。
- C 次之：技术上不确定（密码、系统状态、数据是否还在更新），但一旦确认，工作量可控。它需要现场探索，不适合远程判断。
- A 最低：权限、通道、技术全部明确，两小时能通。放最后，而且它是兜底——即使 B、C 都失败，项目还有一个源可用。

如果反过来从 A 开始，你会到第二周才发现 B 卡住了，那时已经没有调整空间。

**第二题**

最可能漏的是**权限链条上的非技术环节**。

API 是三周里唯一没被验证的假设：「客户会去走商务流程」。而这个流程涉及采购、法务、厂商销售，任何一环卡住，技术准备再充分也没用。

第二个可能是网络策略：API 通了，但客户的出口 IP 在厂商白名单之外，或者需要代理才能出网。

第三个可能是**额度**：接口能调，但标准版的调用额度只够测试，不够生产。

三个都不是技术问题，但它们都在「接入难度」里。这正是本节的主张：难度取决于谁签字，不取决于系统多老——也不取决于你代码写得多好。

## 自检清单

- [ ] 每个源我都能说出「谁签字、周期多久」
- [ ] 至少有一条源，我真实取到过数据（不是看文档）
- [ ] 有一台机器能同时访问源系统与外网
- [ ] 接入顺序按不确定性排，不按重要性排
- [ ] 每个源都有备用路径
- [ ] 我确认过接口额度是否够生产用

> 关于主张的边界：在客户内部团队（甲方自建 FDE）里，「谁有写权限」这个问题会简化——因为权限通常在同一组织内，一个邮件就能协调。这时难度的主导因素会变成「数据分散在几个部门、谁的数字更权威」，属于 6.3 的范畴，而不是权限归属。
