客户说「数据不能出机房」的时候，很多团队的反应是「这项目做不了」，或者「那只能降级做一个演示」。

两种反应都错。真实的约束不会让项目消失，它只会让项目的**形状**改变——变的是你交付什么、怎么验证、迭代多快，不是能不能做。

这一节把变形说清楚，因为不知道会变成什么样，就没法在报价和排期上讲理。

## 现场

锦程精工 A 项目第二轮会议。信息中心主任说了一句：「生产数据不能出这个楼，模型也不能调外部接口。」

团队当场就慌了。方案里所有东西都假设「数据能上云、模型走 API」：向量库是托管的、评测在本地跑完把样本传上去、改一版模型当天生效。

按新约束，这些都不成立。

散了会，项目经理算了一笔账：如果全部本地化，需要买两台 GPU 服务器、部署开源模型、自建向量库、自己维护更新——预算翻三倍，工期加两个月。

但真实的答案没有这么贵。因为约束影响的不是「全部」，是**四个具体环节**。

## 四个环节的变形

**第一，模型部署位置。**

从「调外部 API」变成「本地或客户机房部署开源模型」。代价是：能力上限下降、需要 GPU、升级要重新部署。

这里有个关键取舍：**不是所有场景都需要最强模型。**判定类任务（分类、抽取、匹配）用中等规模开源模型往往够用；生成类任务（写作、长文总结）才吃能力。先确认任务类型，再决定要不要为能力买单。

**第二，日志与样本回传。**

从「全量日志回传，随时分析」变成「只能带回脱敏后的统计，或人工带出的样本」。

这一条对迭代速度的影响最大。原来你可以每天看真实失败案例，现在可能要一周一次，且样本量有限。

应对方式是**在客户侧建一个「问题池」**：系统在本地记录失败案例（脱敏后），每周由客户接口人导出一次给你。这样迭代节奏从「实时」降到「周级」，但链路还在。

**第三，评测方式。**

从「随时拉真实流量做在线评测」变成「离线考题集 + 客户侧人工抽检」。

这意味着第 9 章的双阈值要做调整：在线指标拿不到，只能用「客户每月抽检的纠错率」替代。指标变粗，但仍有约束力。

**第四，变更与升级。**

从「你随时发版」变成「客户走变更流程」。周期从小时级变成周级，而且每次变更要准备回滚方案。

这一条最容易被低估。它意味着你不能「先上线再修」，必须在本地把问题解决干净——这反过来抬高了上线前的验证要求。

## 交付物清单怎么变

这是本节的核心：约束改变的是「交什么」，不是「能不能交」。

| 交付物 | 常规形态 | 不许碰的形态 |
| --- | --- | --- |
| 部署包 | 容器镜像 + 云配置 | 离线安装包 + 依赖清单 + 校验和 |
| 模型 | API 调用 | 权重文件 + 推理服务 + 版本说明 |
| 数据通道 | 实时同步 | 定时导出 + 脱敏脚本 + 人工交接流程 |
| 评测 | 在线指标 | 离线考题集 + 客户抽检表 |
| 运维 | 你远程处理 | 客户能执行的运维手册 + 你远程指导 |
| 升级 | 你发版 | 变更申请单 + 回滚方案 + 客户执行 |

右边这一列，每一项都是额外工作。这就是为什么「不许碰」的项目报价要高——不是因为技术难，是因为**交付物多了一倍，而且大部分是文档和流程**。

同时也解释了另一件事：这类项目的利润往往不差，因为可比的供应商少，而客户也理解约束带来的成本。

## 权限的四种形态

「不许碰」通常伴随权限约束。进场要问清是哪一种，因为它们的技术方案完全不同。

**无统一身份。**每个系统一套账号。方案里不能假设 SSO，要做账号映射表，且要考虑人员变动。

**有 SSO。**统一登录，但通常只覆盖部分系统。要确认哪些系统在 SSO 内、哪些在外。

**行级权限。**同一个系统里，不同人看到不同数据。这类最容易出事——你的取数账号权限过高，会看到不该看的；权限过低，会漏数据。

**多租户。**系统里同时存着多个客户/分公司的数据。取数必须带租户过滤，且要能证明过滤是有效的。

## 验收时最容易被卡的一环

权限相关的验收，失败率比功能验收高得多。三个常见卡点：

**卡点一：审计日志对不上。**客户要求「所有数据访问可追溯」，但你的系统只在应用层记日志，数据库层的访问没记录。补这个往往要改架构。

**卡点二：脱敏不可验证。**你说脱敏了，客户要证明。需要留下脱敏前后的对照样本（在客户侧），以及脱敏规则的版本记录。

**卡点三：权限矩阵没人签。**你列了一张「谁能看什么」的表，但客户内部没人愿意签字确认——因为签了就要负责。

第三个卡点最麻烦，它不是技术问题。应对方式是在项目早期就把这张表拿出来，让业务方和信息安全方一起过一遍，别等到验收前。

## 判据卡

| 判据项 | 合格线 | 不合格信号 | 处置 |
| --- | --- | --- | --- |
| 约束已具体化 | 能说出「什么不能出、出什么程度、谁来判」 | 只有一句「数据不能外传」 | 追问到可执行的粒度 |
| 变形清单已列 | 交付物清单按约束重写过一遍 | 沿用常规清单 | 逐项对照上表重列 |
| 权限形态清楚 | 能说出是四种形态中的哪一种 | 只知道「要开账号」 | 逐系统确认，写进勘察记录 |
| 迭代节奏已定 | 明确了失败案例怎么回来、多久一次 | 假设「随时能看」 | 建问题池，定周级交接 |
| 证据链已设计 | 审计日志、脱敏对照、权限矩阵三样都有安排 | 验收前才想起来 | 早期就拉业务方与安全方过表 |

第二行是本节最实用的检查。**报价前必做**：把常规清单和变形清单并排放，多出来的那部分就是你要报的工。

## 动手练习

**第一题（取舍）**

客户要求全离线部署，但只给一台 24G 显存的机器。你的方案原本用 70B 模型走 API，效果很好。现在有两个选择：

- A. 换 7B 开源模型，效果下降明显，但能跑。
- B. 保持 70B，做量化 + 分片，勉强能跑，但延迟到 8 秒以上。

怎么选？依据是什么？

**第二题（找漏）**

一个「不许碰」的项目顺利上线，三个月后客户要求换供应商。交接时新供应商说「没法接手」。

从交付物清单看，原团队最可能漏了什么？

## 参考答案

**第一题**

先问任务类型，再选。

如果是**判定类**（分类、抽取、匹配），选 A：7B 通常够用，而 8 秒延迟在判定场景里不可接受——用户等不了。

如果是**生成类**（总结、写作、多轮对话），选 B 的变体：保留大模型但限制输入长度、做流式输出，让首字延迟控制在 2 秒内、总时长 8 秒可接受。

如果两类任务都有，正确答案是**拆开**：判定走 7B，生成走量化后的 70B，用路由分发。这比二选一更接近实际工程答案。

这题的关键不是选 A 还是 B，是**不要在没有确认任务类型的情况下做技术选型**。离线约束放大了选型的代价，因为换模型的成本比调 API 高一个量级。

**第二题**

最可能漏的是**可移交性**。

具体三样：

1. **离线安装包与依赖清单。**如果只交付了「装好的系统」而没有可重建的安装包、依赖版本清单、校验和，新供应商无法重建环境。
2. **运维手册。**「不许碰」的项目里，日常运维由客户执行、你远程指导。如果这套指导只存在于你的脑子里和聊天记录里，交接就断了。
3. **模型与数据的版本对应关系。**哪个版本的模型配哪一版的考题集、哪一版的脱敏规则，如果没有记录，新供应商接手后无法判断当前状态是否正常。

这三样都属于「变形清单」里的额外交付物。漏掉它们不会影响上线，只会影响退出——而 FDE 的职业声誉，很大一部分来自退出时是否体面。

## 自检清单

- [ ] 我把「不许碰」追问到了可执行的粒度
- [ ] 我重写过交付物清单，并据此调整了报价
- [ ] 我知道权限属于四种形态中的哪一种
- [ ] 迭代节奏按约束重新设计过（问题池、周级交接）
- [ ] 审计日志、脱敏对照、权限矩阵三样都有安排
- [ ] 交付物里包含可重建的安装包与运维手册

> 关于主张的边界：如果约束导致「模型能力根本达不到业务下限」，那确实不该做——但这时要给出的是能力边界的证据（在同一批考题上，本地模型与目标能力的差距），而不是笼统地说「离线做不了」。用数据拒绝，比用约束拒绝更专业，也更容易被接受。
