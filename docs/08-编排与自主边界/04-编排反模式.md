反模式这个词容易让人以为它们是「写错了」。实际上它们大多写得很漂亮——结构清晰、命名规范、还配了架构图。它们的问题不在代码，在于**用一层技术结构，把一个没想清楚的需求问题糊过去了**。

糊过去的东西不会消失，它会在运行期以另一种形态回来。

## 四种反模式

| 反模式 | 表面症状 | 它在掩盖什么 |
| --- | --- | --- |
| **万能 Agent** | 一个 Agent 挂 20 个工具，什么都能干 | 职责边界不清：不知道该分给谁 |
| **过度分解** | 12 个微 Agent 互相调用，有协调者在中间 | 协作方式不清：不知道谁该先做 |
| **循环兜底** | 失败重试 3 次，再加一个「自愈」Agent | 失败语义不清：不知道什么叫失败 |
| **上下文堆砌** | 把全部历史对话塞进 prompt | 状态定义不清：不知道什么是「当前状态」 |

四种的共同点：**它们都能让系统「看起来在正常工作」，所以能撑过演示，撑不过第三周。**

## 反模式一：万能 Agent

**长什么样。** 一个系统提示词写了三千字，工具清单二十几个，从查询工单到发送邮件到修改配置全在里面。开发者说「这样最灵活，模型自己会选」。

**真正缺什么。** 缺的是「这件事该由谁负责」的答案。当业务方说不清流程分成几段、每段谁负责时，最省事的做法就是全塞给一个 Agent，让它自己看着办。

**为什么演示能过。** 因为演示时输入的是精心挑选的样例，模型的工具选择大体正确。真实场景里，一张「既需要查保修又需要改状态还想顺便通知客户」的工单，会让它连续调五六个工具，中间任何一步选错都不易察觉。

**代价。** 出问题时无法归因。你不知道是提示词没写清、工具描述有歧义、还是模型判断失误。三者混在一起，调试变成猜。

**正确做法。** 按「谁对这个结果负责」切分。每个 Agent（或每条工作流）对应一个明确的责任单元，工具清单控制在 5 个以内。切分依据不是技术，是组织——如果两个动作由不同部门的人负责，它们大概率该分开。

## 反模式二：过度分解

**长什么样。** 一个「调度 Agent」下面挂「查询 Agent」「分析 Agent」「写作 Agent」「审核 Agent」，每个再挂几个工具，中间靠消息传递。架构图很漂亮，像一张组织架构图。

**真正缺什么。** 缺的是「协作顺序」的答案。当需求里没写清「先做什么后做什么」时，画成多个角色互相同步，看起来就把问题解决了。

**为什么演示能过。** 演示时任务简单，各 Agent 各干一段，串起来结果是对的。真实任务里，协调者需要在信息不全时决定「下一步叫谁」，这个决策的质量取决于它拿到的上下文——而上下文在多跳传递中会丢失。

**代价。** 一次任务可能调用十几次模型，成本是单 Agent 的几倍；更麻烦的是错误会沿链条传播，最后一步的错误，根因可能在第一步的措辞。

**正确做法。** 先问「这个任务能不能用一条流水线表示」。能，就用工作流，每步一个函数调用，不需要 Agent。真的需要动态决定顺序时，优先用「单 Agent + 多工具」，而不是多 Agent。8.1 那条经验在这里同样成立：**拆分带来的不是能力提升，是通信开销。**

## 反模式三：循环兜底

**长什么样。** 工具失败了就重试三次；三次还不行，交给一个「自愈 Agent」分析原因并换方案；再不行，降级到一个「兜底回答」。

**真正缺什么。** 缺的是「什么叫失败」的定义。如果 8.2 讲的失败语义没做，工具只会返回空值，那所有失败都长一个样，除了重试没别的办法。

**为什么演示能过。** 演示环境里接口是通的，不会触发重试逻辑。重试分支从来没被执行过，所以看起来是「已处理」。

**代价。** 重试会把瞬时故障放大成持续故障——服务已经在超载，你还给它三倍请求。自愈 Agent 则会制造更难查的问题：它会用另一种方式再试一次，日志里出现两条路径，谁也不知道哪条是对的。

**正确做法。** 先做失败语义（8.2），然后按状态决定动作，而不是按「失败」这个笼统的概念：

| 状态 | 正确动作 |
| --- | --- |
| `timeout` | 重试一次，仍失败则降级 |
| `unavailable` | 不重试，直接降级并告警 |
| `denied` | 不重试，告知用户无权 |
| `invalid` | 修正参数后重试一次 |
| `empty` | 不重试，这不是失败 |
| `partial` | 不重试，明确告知覆盖不全 |

六种状态对应六种动作，其中四种不该重试。**「失败了就重试」这句话，在有了失败语义之后就不成立了。**

## 反模式四：上下文堆砌

**长什么样。** 每轮对话把全部历史拼进 prompt；或者把整个知识库的摘要塞进系统提示词；或者「为了保险」把前 20 条工具返回都留着。

**真正缺什么。** 缺的是「什么是当前状态」的定义。当需求里没说清「任务进行到哪一步、哪一步的结论还算数」时，最省事的做法是全都留着，让模型自己判断。

**为什么演示能过。** 演示的对话短。真实场景跑到第二十轮，上下文里塞着早期已经被推翻的结论、已经失效的中间结果、以及用户随口说的一句「可能吧」。

**代价。** 模型会被早期信息干扰。一个典型现象：用户在第三轮纠正了某个参数，到第十五轮模型又用回了错的那个——因为它在上下文里看到了两次，分不清哪个是后来的。

**正确做法。** 显式维护状态，而不是靠上下文堆积。状态至少包含：

- 任务当前进行到哪一步
- 已经确认的事实（带来源）
- 已被推翻的假设（明确标记，不要静默丢弃）
- 待确认的问题

有了这份状态，上下文只需要带「状态 + 最近几步」，长度可控，且不会自相矛盾。

## 一个统一的识别方法

四种反模式都能用同一个问题识别出来：

> **这个技术结构在替谁做决定？如果把它删掉，会暴露出什么需求问题？**

- 删掉万能 Agent 的「灵活」，暴露的是职责没划分。
- 删掉多 Agent 的「协作」，暴露的是顺序没定义。
- 删掉重试的「自愈」，暴露的是失败没分类。
- 删掉堆砌的「上下文」，暴露的是状态没定义。

四个暴露出来的东西，都不是技术问题，是需求问题。这就是为什么加结构没用——**结构能吸收模糊，但不能消除模糊。**

## 什么时候加结构是对的

不是所有复杂结构都是反模式。判断标准是：**这个结构在解决一个已经被写清楚的问题，还是在回避一个没写清楚的问题。**

合法的复杂结构：

- 任务确实需要动态决定下一步（诊断类），所以用 Agent 循环。
- 子任务确实可以并行且互不依赖，所以用并行编排。
- 失败确实需要分类处理，所以有分支状态机。

不合法的复杂结构：

- 因为「不知道该怎么分」，所以全给一个 Agent。
- 因为「说不清先后」，所以让多个 Agent 自己协商。
- 因为「不知道什么算失败」，所以一律重试。
- 因为「不知道什么是当前状态」，所以全都留着。

区别在于：前者的复杂是**问题本身要求的**，后者的复杂是**逃避问题产生的**。前者会随需求清晰而稳定，后者会随需求清晰而崩溃——因为它本来就是为了不清晰而建的。

## 判据卡

| 判据项 | 合格线 | 不合格信号 | 处置 |
| --- | --- | --- | --- |
| 职责可归因 | 出问题时能指出是哪个责任单元 | 一个 Agent 承担多种职责 | 按责任切分，工具数控制在 5 个内 |
| 结构有依据 | 每个复杂结构都能对应一条写清楚的需求 | 结构图无法用一句需求解释 | 删掉，退回更简单的形态 |
| 失败分类 | 按状态决定动作，不是一律重试 | 代码里有 `retry(3)` 但没有状态判断 | 先做失败语义，再谈重试 |
| 状态显式 | 有独立的状态对象，不是靠上下文堆积 | 每轮都拼全部历史 | 建状态，上下文只带状态 + 最近几步 |
| 成本可解释 | 能说出为什么这个任务要这么多次模型调用 | 没算过，或算过但说不清必要性 | 算一遍，多数情况会发现可以减半 |

## 动手练习

**第一题（找漏）**

一个团队的编排是这样的：一个主 Agent 接收用户请求，判断类型后分给四个子 Agent（查资料、算数据、写报告、审报告），子 Agent 之间可以互相调用，任一子 Agent 失败会重试三次。他们声称「这样最健壮」。

请指出至少三个问题，并说明各自会在真实场景里导致什么。

**第二题（取舍）**

你的 Agent 在处理第 15 轮对话时，用回了第 3 轮已经被用户纠正过的一个参数。日志显示上下文里两处都有，模型选了先出现的那处。你会怎么改？给出两个方案，并说明各自的代价。

## 参考答案

**第一题**

1. **「子 Agent 之间可以互相调用」= 没有明确的执行顺序。** 这掩盖了「协作方式不清」的问题。真实后果：查资料的和算数据的互相等对方的结果，形成循环，或者重复劳动。更糟的是无法预测一次任务要跑多久。
2. **「主 Agent 判断类型后分派」= 分类规则没有写下来。** 如果分类逻辑只存在于提示词里，那它每次可能不同。真实后果：同一个请求两次被分给不同子 Agent，输出风格与深度都不一致。
3. **「失败重试三次」= 没有失败语义。** 真实后果：如果失败原因是「无权限」，重试三次等于三次无用请求；如果是「服务不可用」，重试会放大故障。「审报告」子 Agent 的重试尤其危险——它可能把一份已经合格的报告反复改写。
4. **（补充）四个子 Agent 的边界可能重叠。** 「写报告」和「审报告」如果是同一个模型扮演，实际上是自己审自己，这个环节没有独立价值。

正确做法：先确定这是不是一条流水线。如果是（大概率是），改成四步工作流，每步一个函数 + 明确输入输出，去掉互相调用，去掉无差别重试。

**第二题**

**方案一：显式状态对象。**

维护一个结构化的状态，包含「已确认事实」与「已推翻假设」，每轮只把状态和最近三步放进上下文。被纠正的参数写入状态时覆盖旧值，并把旧值记入「已推翻」。

代价：需要改上下文组装逻辑，且状态结构要设计得当——设计不好的话会丢信息。收益是彻底的：不会再有「两处都有」的情况。

**方案二：在上下文里显式标注时序。**

不改状态结构，但在拼接历史时给每条加标记：「第 3 轮（已被第 5 轮更正）」「第 5 轮（当前有效）」。让模型看到的是带修订痕迹的对话。

代价：上下文长度不降，只是加了标记；模型仍可能忽略标记（概率降低但没消除）。好处是改动小，可以立即上线。

**我倾向先做方案二，两周内做方案一。** 理由：方案二能立刻止血，而且它产生的「修订标记」正好是方案一需要的数据结构雏形。直接从方案一开始，容易因为设计不当而返工。

但有个前提：如果这个问题已经导致过事故，就直接上方案一，不要再等。
