「能不能做成 Agent」这个问题问错了。正确的问题是：**这件事的步骤能不能事先写下来，写错一步的代价有多大。**

这两个问题的答案组合起来，才决定该用工作流还是 Agent。而绝大多数被叫作 Agent 的东西，其实是一张画得很复杂的流程图。

## 现场

锦程精工的售后工单处理，客户提的需求是：「做一个智能 Agent，自动处理售后工单。」

团队问流程，售后主管在白板上画了五步：接单 → 判断是否在保修期内 → 识别故障类型 → 匹配工程师 → 派单并通知。

每一步都有明确的判断依据：保修期查合同表，故障类型查故障码表，工程师匹配看技能标签和当前负荷。分支不少——保修内走 A 流程，保修外走 B 流程，紧急工单插队，跨区域要转派——但每一步的判断依据是清楚的、可枚举的。

团队还是做成了 Agent。理由是「分支太多，写 if-else 太丑，让模型自己判断更灵活」。

上线两周，问题出来了：

- 同一张工单，早上跑和下午跑，结果不一样。因为模型对「紧急」的理解有波动。
- 有一张工单被判成保修外，客户投诉。查日志，模型在「判断保修期」这一步读了合同表，但把「质保起始日」理解成了「合同签署日」。
- 有个工单在「匹配工程师」和「通知」之间循环了四次，因为通知工具返回了一个模型没预期的格式，它选择了重试。

三件事的共同点：**这些步骤本来是可以确定的，是团队主动把它变成了不确定的。**

## 两个条件，缺一不可

判断该不该用 Agent，只看两件事。

**条件一：步骤不可预知。** 注意是「不可预知」，不是「分支多」。分支多但每条分支的条件明确，那是复杂的流程，不是不可预知。

判别方法：**你能不能写出一个覆盖 95% 情况的流程图？** 能，就是可预知。锦程精工这个案子，流程图两页纸能画完，属于可预知。

**条件二：失败可承受。** 错了会怎样？如果错了要返修、要赔偿、要对外解释，那就是不可承受。

两个条件组成四象限：

| | 失败可承受 | 失败不可承受 |
| --- | --- | --- |
| **步骤可预知** | 工作流（最简单的那种） | **工作流 + 关键节点人工确认** |
| **步骤不可预知** | Agent | 人来做，Agent 只做辅助 |

四个格子里的选项都不含「先试试 Agent 看看」。这不是保守，是因为 Agent 的代价不在开发期，在运行期——它每次执行都可能走不同的路，而你要为每一条路负责。

锦程精工这个案子落在左上或右上：步骤可预知，派错工程师的代价中等（可回退，但要道歉）。所以正确答案是工作流，在「判断保修期」这一步加人工确认——因为那一步错了要赔钱。

## 什么叫「步骤不可预知」

举三个真实成立的例子，和三个看起来像但不成立的。

**成立的：**

1. **故障诊断。** 工程师描述现象，要一路问下去：噪音大吗？压力正常吗？最近换过油吗？下一步问什么，取决于上一步答什么。分支无法预先枚举，因为用户的回答本身是开放的。
2. **数据探查。** 「上季度华北区返修率为什么上升」——要先看总体，再拆区域，再拆型号，可能还要看时间分布。查什么取决于看到了什么。
3. **跨系统对账。** 两个系统的数据对不上，要逐层往下钻，钻到哪一层取决于差异出现在哪。

**不成立的：**

1. **客服问答。** 看起来开放，实际是「检索 + 回答」两步，答案形态固定。这属于第 7 章的三类划分里的查表/规则/检索，不是编排问题。
2. **工单派发。** 分支多，但条件明确。属于复杂流程。
3. **报告生成。** 模板固定，数据来源固定，属于工作流。

一个简单的判据：**如果两个资深员工做同一件事，步骤会不一样，才叫不可预知。** 如果他们的步骤一样、只是判断依据的取值不同，那是流程。

## 工作流的三种形态

选定工作流之后，也不是只有「一串 if-else」。三种形态覆盖绝大多数场景：

| 形态 | 适用 | 实现要点 |
| --- | --- | --- |
| **线性** | 步骤固定、无分支 | 每步有明确的输入输出，失败即中断并告警 |
| **分支（规则）** | 条件明确、可枚举 | 规则表外置，业务方能自己改；不要在代码里写死 |
| **并行 + 汇总** | 多个独立子任务 | 明确「部分失败」怎么算——全成功才继续，还是尽力而为 |

第三种最容易出问题。三个子任务并行，两个成功一个超时，整体算成功还是失败？这个决定必须在设计时做，而不是等它发生。

规则表外置这一条值得展开：如果分支条件是业务规则（保修期怎么算、什么算紧急），把它做成配置表，业务方能改。写在代码里，每次调整都要发版，最后的结果是「规则永远停在第一版」。

## Agent 的三种适用形态

真的落在「不可预知 + 可承受」象限时，Agent 也有形态之分：

**受限循环（最常用）。** 给一组工具、一个明确的终止条件、一个最大步数。适合诊断类任务。关键是终止条件要可判定，不能是「模型觉得可以了」。

**计划-执行两段式。** 先让模型出一份计划（可人工审阅），再逐步执行。适合步骤较长、中间可以检查的任务。代价是多一次模型调用。

**多 Agent 协作（慎用）。** 拆成多个角色互相通信。它的成本是指数级的——不只是 token，还有调试难度。没有明确的职责边界时，多 Agent 会把「谁该做什么」的模糊放大成「谁都没做」或者「重复做了三遍」。

一条经验：**能用单 Agent 加更多工具解决的，不要拆成多 Agent。** 拆分带来的不是能力提升，是通信开销。

## 成本的量级差异

这一点常被忽略。同一个任务，工作流和 Agent 的成本不在一个量级：

| 维度 | 工作流 | Agent |
| --- | --- | --- |
| 单次 token | 基准 | 3–10 倍（循环 + 每步都要带上下文） |
| 延迟 | 可预估（各步耗时之和） | 方差大（步数不定） |
| 可测试性 | 每步可单测 | 只能端到端测，且结果不稳定 |
| 出错定位 | 日志能看到断在哪一步 | 要看完整轨迹才知道它为什么这么走 |
| 改需求的成本 | 改一个节点 | 可能要重新调提示、换工具、改终止条件 |

第三行（可测试性）是最容易被低估的。工作流的每一步可以单独验证，Agent 只能整条链路跑。而整条链路的输出不稳定，意味着「跑通了」这件事本身不可复现。

## 判据卡

| 判据项 | 合格线 | 不合格信号 | 处置 |
| --- | --- | --- | --- |
| 步骤性质已判定 | 明确回答「能否画出覆盖 95% 的流程图」 | 用「分支太多」当作选 Agent 的理由 | 画流程图，画得出来就是工作流 |
| 失败代价已评估 | 写清了错一步的后果与可逆性 | 只说「先做出来看看」 | 按四象限重新选型 |
| 关键节点有闸 | 不可逆或高代价的步骤有人工确认 | 全流程无人干预 | 在该步插入确认点，不是整体加审核 |
| 终止条件可判定 | Agent 的停止条件是可检查的状态，不是「模型认为完成」 | 文档写「模型判断任务完成」 | 改成显式条件 + 最大步数 |
| 规则可外置 | 业务规则在配置表里，业务方能改 | 规则硬编码，改一次发一次版 | 外置，这条决定系统能不能活过三个月 |

## 动手练习

**第一题（判定）**

下面四个需求，分别该用工作流、工作流+人工确认、Agent，还是人做+Agent 辅助？各说明理由。

1. 自动处理售后工单派发（保修判断、故障分类、工程师匹配）
2. 帮工程师诊断设备异响原因（一路追问现象）
3. 自动生成给客户的月度维保报告
4. 自动决定给哪个客户延长保修期

**第二题（取舍）**

客户坚持要用 Agent 做工单派发，理由是「我们的流程经常变，写死了不好改」。你怎么回应？写出你的判断，以及在什么条件下你会同意用 Agent。

## 参考答案

**第一题**

1. **工作流。** 五步都可枚举，条件是明确的（保修期查表、故障类型查码、工程师看标签）。分支多不等于不可预知。派错人的代价可回退，所以未必需要人工确认，但「保修判断」这一步建议加，因为错了要赔钱。
2. **Agent。** 这是四象限里最典型的「不可预知 + 可承受」：追问路径取决于用户回答，无法枚举；诊断错了工程师会发现（他有专业判断），代价可承受。
3. **工作流。** 模板固定、数据来源固定、步骤固定。这里用 Agent 属于过度设计。
4. **人做，Agent 辅助。** 延长保修期是商务决策，涉及金额与责任，失败不可承受。Agent 可以做的是「整理该客户的维保记录、返修频次、历史让步情况」，供人判断。这个案子的关键是把「辅助」和「决定」分开。

**第二题**

回应分三步：

**第一步，区分「流程变」和「判断依据变」。** 大多数情况下，客户说的「流程经常变」，实际是「规则参数经常变」——保修期从 12 个月改成 18 个月，紧急工单的判定阈值调整，区域划分变化。这些是参数，不是流程。参数外置成配置表，业务方自己改，不需要 Agent，也不需要发版。

**第二步，指出 Agent 解决不了这个问题。** 如果流程真的经常变，Agent 的提示词、工具集、终止条件同样要跟着改——而且因为它是不确定执行，改完你还得重新验证一遍。变更成本不是降低，是升高了，只是从「改代码」变成了「改提示词再重测」。

**第三步，给条件。** 我会同意用 Agent，如果同时成立三条：

- 客户能举出三个具体的例子，说明流程的哪一步「事先无法确定下一步」；
- 这三步的失败可以被下游发现并纠正，不需要返工；
- 客户接受「同一张工单两次处理结果可能不同」，并认可这是可接受的行为。

三条里任何一条不成立，就退回工作流。

这里有个沟通要点：不要说「你们的需求错了」，说「我们先把确定的部分做成确定的，把不确定的部分留给模型」。客户听到的是风险控制，不是技术偏好。

## 自检清单

- [ ] 我能画出这件事的流程图，并覆盖 95% 的情况
- [ ] 我知道错一步的代价，以及能不能回退
- [ ] 我的选型能对应到四象限里的某一格，而不是「先试试」
- [ ] 如果用了 Agent，终止条件是可检查的状态而不是模型的自我判断
- [ ] 业务规则在配置表里，不在代码里
- [ ] 我知道这个方案的 token 成本大约是工作流的几倍

> 关于主张的边界：当任务本身还在探索期、连流程都还没定型时，先用 Agent 跑几遍、观察它怎么走，是一种合理的发现手段——它能把隐性的步骤暴露出来。但这是**调研手段**，不是交付形态。观察完之后，该固化成工作流的部分要固化，不能把探索期的形态直接推上线。
