每份交付文档里都有一节叫「系统边界」，写着「系统不会自动执行 X」「涉及 Y 的操作需人工确认」。这一节的实际约束力是零——因为它约束的是读文档的人，而系统执行的是代码。

边界只有三种真实形态：**调不到、要确认、能撤销**。除此之外的一切表述，都只是意向。

## 现场

锦程精工的工单 Agent，交付文档第 4.2 节写着：

> 系统不会自动向客户发送任何通知。所有对外沟通均需人工确认后由系统生成草稿。

写得清楚，客户也认可。上线两周后，一位客户的手机收到一条短信：「您的设备维修已完成，工单 #12345 已关闭，请对本次服务评分。」

客户打电话来问：「你们什么时候开始自动发短信了？」

查日志：Agent 在处理一张工单时，调用了 `notify_customer` 工具。这个工具在工具清单里，因为「生成草稿」和「发送通知」是同一个工具的两个参数——`dry_run=True` 生成草稿，`dry_run=False` 直接发。Agent 在某次调用里填了 `False`。

事后复盘，责任很清楚，但也很尴尬：**文档写了不做的事，代码做了。** 文档没有错，代码也没有「违背」文档——它们根本不在同一个系统里。文档约束的是人，代码约束的是系统，而人不会在每次调用前读一遍 4.2 节。

## 边界的三个位置

边界要落在系统里，只有三个位置可以落：

| 位置 | 机制 | 能挡住什么 | 挡不住什么 |
| --- | --- | --- | --- |
| **事前** | 工具白名单 / 权限 | 系统根本调不到这个能力 | 白名单内的操作做错 |
| **事中** | 人工确认 / 草稿模式 | 高代价操作执行前被拦下 | 人看也不看就点确认 |
| **事后** | 审计日志 / 可撤销 | 出了问题能定位、能回退 | 已经造成的对外影响 |

三层不是替代关系，是叠加关系。上面那个短信事故，三层都缺：

- 事前没做：`notify_customer` 在工具清单里，Agent 能调。
- 事中没做：调用没有确认环节，`dry_run` 只是一个参数，模型可以自己填。
- 事后弱：有日志，但短信已经发出去了，撤不回。

修法也不是只补一层：

1. **事前**：把「发送通知」从 Agent 的工具清单里删掉。Agent 只能用 `create_draft`，它的返回是一条待审草稿。
2. **事中**：草稿进入人工审核队列，审核人看到收件人、内容、触发原因。
3. **事后**：所有对外发送记录留痕，谁审的、什么时候发的、原文是什么。

关键在第一层。**能用「调不到」解决的，不要用「要确认」解决。** 因为确认会被疲劳消解——审核到第 200 条时，人会开始不看内容直接点通过。

## 四种产品形态

把边界做成产品，有四种形态，可靠性依次下降：

**第一种：能力不给。** 系统根本没有这个工具。最可靠，但最不灵活。

**第二种：草稿模式。** 系统能生成，但不能执行。产物是一个待处理对象（草稿、待审单、建议），人处理它。这个形态适合 80% 的场景，因为它保留了自动化的大部分价值，同时把不可逆的动作留给人。

**第三种：确认弹窗。** 系统要执行时弹窗，人点确认。比草稿弱，因为弹窗容易被无脑点过；比没有强。适合低频、高代价的操作。

**第四种：可撤销。** 系统直接执行，但留一个撤销窗口（30 秒、5 分钟、24 小时）。适合高频、影响可逆的操作。

选择依据是一张表：

| 操作特征 | 推荐形态 |
| --- | --- |
| 不可逆 + 高代价 | 能力不给，或草稿 + 人工审核 |
| 不可逆 + 低代价 | 确认弹窗 |
| 可逆 + 高代价 | 确认弹窗 + 撤销窗口 |
| 可逆 + 低代价 | 直接执行 + 撤销 |

「不可逆 + 高代价」这一格最需要警惕，因为团队常把它做成「确认弹窗」——而弹窗是四种形态里最容易被绕过的一种，尤其在操作频繁的时候。

## 边界要能被看见

前三种形态都有一个隐含要求：**用户得知道边界在哪。**

如果系统只会在某些时候弹确认框，用户无法预判哪些操作会被拦。这会导致两种行为：要么过分谨慎（每一步都怕），要么过分信任（以为不弹就是安全的）。

所以边界需要一层「说明书」，但不是在文档里，是在界面上：

- 工具清单页面：列出系统能做的全部动作，以及每个动作的形态（自动 / 需确认 / 仅草稿）。
- 执行轨迹：一次任务结束后，展示「它做了哪几步、哪几步是你确认过的、哪几步是它自己决定的」。
- 权限说明：当前用户能触发哪些动作，不能触发哪些。

第二条（执行轨迹）是 8.4 讲审计时的基础，也是这里判断边界是否真的落地的证据。**如果用户看不到「哪几步是它自己决定的」，那这条边界对他而言就不存在。**

## 一个可执行的验收方法

L2 判据的核心是「可被未参与者验证」。具体做法：

> 找一个没参与开发的人，让他用这个系统完成一个真实任务。结束后问他三个问题：
>
> 1. 刚才系统做了哪几件事？
> 2. 哪几件是它自己决定的，哪几件是你确认过的？
> 3. 如果它想做一件你不希望它做的事，会不会被拦住？你怎么知道？

三个问题都答得上来，边界才算落在产品里。任何一个答不上来，说明边界还停在文档上。

这个方法的好处是它不依赖开发者的自我陈述。开发说「我们做了权限控制」，用户说「我不知道它能做什么」——两个都真，但后者才是系统的实际状态。

## 判据卡

| 判据项 | 合格线 | 不合格信号 | 处置 |
| --- | --- | --- | --- |
| 高风险能力不可达 | 不可逆 + 高代价的操作，Agent 的工具清单里没有 | 工具在清单里，靠参数或提示词约束 | 从清单移除，改成草稿接口 |
| 形态与代价匹配 | 按四象限选择了形态，且有理由 | 所有操作都用确认弹窗 | 重新分类，高代价的降级为草稿 |
| 边界可见 | 界面上有工具清单与执行轨迹 | 用户只能从文档了解边界 | 加轨迹展示，这是最有效的一步 |
| 确认有信息 | 确认框展示了「将发生什么」的具体内容 | 确认框只写「是否继续」 | 补预览：对象、内容、影响范围 |
| 未参与者可验证 | 按上面三个问题测过，能答上来 | 只有开发者能解释边界 | 补界面，别补文档 |

## 动手练习

**第一题（判定）**

下面四个操作，分别该用哪种产品形态（能力不给 / 草稿 / 确认 / 可撤销）？说明理由。

1. 向客户发送维修完成短信
2. 在内部系统中把工单状态从「处理中」改为「已完成」
3. 删除一条重复的工单记录
4. 给工程师推荐下一位可派单的人选

**第二题（找漏）**

一个系统的交付文档写着：「Agent 的所有操作都在人工监督下进行，关键步骤会请求确认。」你去验收，发现界面上只有一个「开始」按钮，点击后系统自动跑完，最后给出一份结果。你判断这条边界成立吗？需要补什么？

## 参考答案

**第一题**

1. **草稿 + 人工审核。** 对外沟通不可逆（短信发出去就收不回），且影响客户关系。系统生成草稿、审核人确认发送，是唯一稳妥的形态。这个案子里 `dry_run` 参数的设计本身就是错的——它把「安全模式」做成了一个可以被模型填的开关。
2. **直接执行 + 撤销窗口。** 状态变更影响内部流程，客户感知弱，且可改回。给一个 5 分钟撤销窗口即可，不必每次确认——工单状态变更太频繁，每次弹窗会导致审核疲劳。
3. **确认，或干脆能力不给。** 删除是典型的不可逆操作。如果业务上确实需要，做成「标记删除 + 定期清理」，让 Agent 只能标记，真删由人执行。
4. **直接执行（其实是纯建议）。** 这不是「执行一个动作」，是「给出一个建议」，本身没有副作用。但要注意：如果推荐结果会直接影响派单，那它就变成了一个决策输入，需要能解释「为什么推荐这个人」——否则派错了没人知道该改什么。

**第二题**

边界不成立。理由：文档说的「关键步骤会请求确认」，在界面上完全没有体现；用户看到的是一次黑箱执行。这属于 8.3 开头那类情况——文档约束了人，代码没有对应实现。

要补四样：

1. **执行轨迹。** 跑完之后展示每一步：调了什么工具、参数是什么、返回是什么、哪几步是自动的。这是最低要求。
2. **确认点**。识别出流程里的不可逆步骤，在那里真的停下来等人。停下来的时候要展示「将要发生什么」，不是「是否继续」。
3. **工具清单页。** 让用户事先知道系统能做什么。
4. **重跑那三个问题。** 补完之后找一个没参与的人再测一次——如果他能说清「哪几步是它自己决定的」，才算过。

补充一点：如果系统确实设计成「一键跑完」，那也没问题——但交付文档必须改成「系统全自动执行，边界由权限控制保证」，而不是「关键步骤会请求确认」。**文档与实现不符，比没有文档更糟**，因为它会让验收方以为边界存在。

## 自检清单

- [ ] 高风险能力不在 Agent 的工具清单里，而不是靠提示词约束
- [ ] 每个操作的形态与它的代价匹配，不是一律弹确认
- [ ] 界面能看到「系统做了什么、哪些是自己决定的」
- [ ] 确认框展示的是具体内容与影响，不是「是否继续」
- [ ] 有一个没参与开发的人，按三个问题测过
- [ ] 交付文档里的边界描述，与代码实现一一对应

> 关于主张的边界：在内部工具、低风险场景里（比如给员工查资料），过度的边界设计会显著降低效率，这时候「先放开、有问题再收」是合理的。判断标准还是那条：错了会不会有人受损。不会，就可以松；会，就必须落到产品里。
