给 Agent 加工具的时候，所有人的注意力都在「这个工具能干什么」。但真正决定 Agent 可不可靠的，是**这个工具在失败时说了什么**。

一个能力很强、但失败时沉默的工具，会让 Agent 走上一条看起来很合理的错路。而一个能力一般、但失败时说得清楚的工具，Agent 至少知道自己走到了死胡同。

## 现场

锦程精工的诊断 Agent，接了一个「查询历史工单」的工具。第一次实现是这样的：

```python
def query_tickets(equipment_id: str) -> list:
    resp = http.get(f"/api/tickets?equipment={equipment_id}")
    if resp.status != 200:
        return []          # 出错就返回空
    return resp.json()["items"]
```

这个实现里，「这个设备没有任何历史工单」和「接口挂了」和「你没权限查」和「设备号写错了」，返回的是同一个东西：一个空列表。

上线第三天，一张工单出了事故。过程是这样的：

1. 工程师报「XX-200 液压站压力不稳」。
2. Agent 查该设备的历史工单，得到 `[]`。
3. Agent 的推理是：没有历史工单 → 这是一台新设备或首次故障 → 建议按标准流程全面排查。
4. 实际上这台设备有 11 条历史工单，其中 7 条是同一个压力问题，而且两个月前刚换过蓄能器。
5. 全面排查花了 4 小时，而正确答案在第一条历史工单里。

走查日志的时候，第 2 步是唯一的问题点。Agent 没有做错任何推理——它拿到的信息是「没有历史」，那么推理完全正确。

**错的不是推理，是工具说了谎。**

## 「空」这个词承担了太多含义

在人类使用的界面里，空列表是有上下文的：用户知道刚才有没有转圈、有没有报错提示。但 Agent 看到的是一个数据结构，它没有界面，没有「刚才转了两秒才出结果」这种感知。

所以工具必须把「为什么是空的」编码进返回值。至少六种情况要分开：

| 状态 | 含义 | 模型应该做什么 | 如果不区分会怎样 |
| --- | --- | --- | --- |
| `ok` | 查到了，有结果 | 使用结果 | — |
| `empty` | 查了，确实没有 | 可以基于「没有」继续推理 | — |
| `denied` | 无权限 | 停下来，告知用户 | 会当成「没有」，继续错下去 |
| `timeout` | 超时 | 重试或换路径 | 同上，且会重复超时 |
| `invalid` | 参数不合法 | 修正参数重试 | 会当成「没有」，且永远错 |
| `unavailable` | 服务不可用 | 停止，不要重试 | 会疯狂重试直到耗尽步数 |
| `partial` | 有结果但不完整（分页/截断） | 明确告知覆盖不全 | 会把部分当全部，下结论 |

七个状态里，`partial` 最容易被忽略，也最隐蔽。模型查到 20 条记录，实际有 200 条，前 20 条恰好都不相关——它会得出「没有相关记录」的结论，而这个结论看起来是有依据的。

## 返回结构长什么样

不需要复杂，三个字段够用：

```json
{
  "status": "empty",
  "data": [],
  "hint": "该设备在近 24 个月内无工单记录。若这是新装机设备，可继续按标准流程排查；若设备已服役，请确认设备编号是否正确。"
}
```

`status` 给机器判断，`hint` 给模型决策。

`hint` 这一栏是最有价值的，也是最容易被省掉的。它不是给人看的错误提示，是给模型的**下一步建议**。上面这个例子，如果 hint 写了「请确认设备编号」，Agent 就会去核对编号，而不是直接跳到「新设备」的结论。

写 hint 的要点：

- 说清「这意味着什么」，而不只是「出了什么错」
- 给出可执行的下一步（重试 / 换参数 / 停下来问人）
- 明确「不要把这种情况当成什么」

最后一条尤其重要。比如权限不足时，hint 应该写「不要基于此结果推断数据不存在」。

## 工具描述也是设计的一部分

模型唯一能看到的是工具的名称、描述、参数说明。它看不到实现。

这带来一个反直觉的结论：**工具描述写得含糊，比实现写得差更致命。**

反例：

```text
query_tickets(equipment_id: str) -> list
查询工单。
```

模型会怎么理解这个工具？它不知道返回什么结构、不知道失败时是什么样、不知道有没有分页。它只能试。

正例：

```text
query_tickets(equipment_id: str, limit: int = 20) -> dict
按设备编号查询历史工单，按时间倒序返回。

返回 {"status", "data", "hint"}：
  status = ok / empty / denied / timeout / invalid / unavailable / partial
  data 为工单列表，每项含 ticket_id, date, fault_type, resolution

注意：
  - 单次最多返回 limit 条，若 status=partial 说明还有更多
  - status 不为 ok 时，不要基于 data 推断任何结论
  - 设备编号必须与资产系统一致（格式 XX-NNN）
```

描述里那三条「注意」，每一条都对应一类真实事故。

## 幂等与重试

Agent 会重试。这是它的本能，也是必要的——超时了就再试一次是合理的。

但如果工具不幂等，重试会制造副作用。最常见的坑是「创建类」工具：Agent 调用「创建工单」超时了，它重试，于是创建了两张。

处理办法有三层：

1. **读写分离。** 读工具可以随便重试，写工具必须带幂等键（客户端生成一个 request_id，服务端去重）。
2. **写工具返回明确的「已执行」状态。** 如果超时后不知道有没有成功，工具应该提供「按 request_id 查询执行结果」的接口。
3. **把「不确定是否执行」当成一个显式状态。** 这种情况不该让 Agent 自己决定重试，应该停下来问人。

第三层最关键。**「不知道有没有成功」是比「失败」更危险的状态**，而多数工具没有表达它的位置。

## 危险操作怎么让模型知道危险

模型不知道什么叫「危险」。它只看到工具名和描述。

所以危险必须写在工具的形态里，而不是写在文档里。三个做法，从弱到强：

**第一，命名。** `delete_ticket` 比 `remove_record` 明确。`send_email_to_customer` 比 `notify` 明确。命名里带上对象和不可逆性。

**第二，返回值里带确认。** 危险工具第一次调用不执行，返回：

```json
{"status": "needs_confirmation", "preview": "将向客户 张三（1380****）发送邮件，主题：…，内容：…", "confirm_token": "…"}
```

模型必须用 `confirm_token` 再调一次才真的执行。这一步把「不可逆」变成了「两步走」。

**第三，权限在服务端。** 无论 Agent 怎么调，服务端检查调用方有没有权限。这一层不能指望 Agent 自觉。

三层都要有。只做第一层是自欺，只做第二层挡不住被绕过的提示，只做第三层的话，Agent 会一直撞墙但不知道为什么。

## 判据卡

| 判据项 | 合格线 | 不合格信号 | 处置 |
| --- | --- | --- | --- |
| 失败状态可区分 | 读工具至少区分 ok / empty / denied / timeout / invalid / unavailable / partial 七种 | 出错统一返回空值或 None | 改返回结构，这是最高优先级 |
| 有 hint | 每个非 ok 状态都给出下一步建议与「不要推断什么」 | 只有错误码 | 补 hint，它比错误码更有用 |
| 描述可决策 | 工具描述里写清返回结构、失败语义、使用限制 | 描述只有一句话 | 重写描述，模型只看得到这个 |
| 写操作幂等 | 写工具带幂等键或可查执行结果 | 超时后无法确认是否已执行 | 加幂等键 + 结果查询 |
| 截断显式 | 分页/截断时返回 partial 并说明总数 | 只返回前 N 条，不说明 | 补 total 字段与 partial 状态 |
| 危险可识别 | 危险工具名明确、有二次确认、服务端有权限校验 | 靠文档提醒「不要调用」 | 三层都要补 |

## 动手练习

**第一题（找漏）**

下面这个工具定义有什么问题？至少说出三项，并说明各自会导致什么后果。

```python
def search_knowledge(query: str) -> str:
    """搜索知识库，返回相关内容。"""
    ...
    return "\n".join(docs)   # 没找到时返回空字符串
```

**第二题（取舍）**

你的 Agent 需要调用一个「修改工单状态」的工具。这个操作会触发客户短信通知，改错了要打电话道歉。工具的底层 API 只提供了 `PUT /tickets/{id}`，超时时无法知道有没有改成功。你怎么设计这个工具？

## 参考答案

**第一题**

至少四个问题：

1. **返回类型是字符串，没有状态位。** 没找到返回空字符串，失败也可能返回空字符串。后果：模型无法区分「没有」和「没查到」，会基于错误的「没有」继续推理——这正是 8.2 开头那个事故。
2. **描述没说返回什么结构。** 「返回相关内容」——几条？什么格式？有没有出处？后果：模型对结果的预期不稳定，可能把拼接后的长文本当成一条完整答案。
3. **没有说明未找到时返回什么。** 后果：模型看到空字符串，可能理解为「查询失败」而无限重试，也可能理解为「没有相关内容」而给出错误结论。两种都可能。
4. **没有出处信息。** 拼接 `docs` 时丢掉了文档名与位置。后果：结果不可追溯，直接违反 7.3 的要求。

改进方向：返回 `{status, data: [{content, source, doc_version, locator}], hint}`；`status` 至少区分 ok / empty / invalid / unavailable；描述里写清每项结构。

**第二题**

设计要点四条：

1. **加幂等键。** 即使底层 API 不支持，也应该在工具层维护一个 request_id → 执行结果的对照表（可以存在本地或轻量存储）。超时后用 request_id 去查「这次修改到底成功没有」。
2. **把「不确定」当成独立状态。** 返回 `{"status": "unknown", "hint": "无法确认上次修改是否生效，请勿直接重试。先用 get_ticket_status 查询当前状态。"}`。这一条是核心——不让模型自己猜。
3. **加二次确认，且预览要能看到后果。** 第一次调用返回 `needs_confirmation`，preview 里写明「工单 #12345 将从『处理中』改为『已完成』，将向客户张三（尾号 8899）发送短信」。模型确认后才执行。
4. **工具描述里写清副作用。** 「本工具会触发客户短信通知，且不可撤回」。模型看到这句话，在不确定时更倾向先查后改。

补充一条工程上的建议：**这个工具应该关联一个「撤销窗口」**。修改后 5 分钟内允许改回，且这段时间内不发短信。把「不可逆」变成「短暂可逆」，成本远低于事后道歉。

> 关于主张的边界：当工具的下游系统本身就不提供错误区分时（比如一个老接口只会返回 200 或 500），要补全七种状态确实做不到。这种情况下至少要做到两件事：把「有结果」和「没结果」分开，以及在所有非确定性情况下返回 `unavailable` 而不是 `empty`。宁可让 Agent 多停下来几次，也不要让它带着错误前提往下走。
