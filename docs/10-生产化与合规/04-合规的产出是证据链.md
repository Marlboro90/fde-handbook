合规评审最容易失败的方式，不是系统做得不合规，是**做了但证明不了**。

「我们对数据做了加密」「我们有访问控制」「我们保留了审计日志」——这三句话在评审会上没有一句能过关，因为评审方要问的不是「有没有」，是「凭什么信」。

## 现场

锦程精工的 A 项目要过一次等保测评。团队准备得很认真：四十页材料，包括安全承诺书、架构图、数据流程图、权限设计说明、还有一份「安全管理制度」。

评审会开了四十分钟，专家问了三个问题：

1. 「数据传输加密，用的是什么算法、什么版本？」
2. 「密钥由谁管理，轮换周期多久，上次轮换是什么时候？」
3. 「审计日志能不能证明没有被删改过？」

三个问题，团队答得都不完整：

1. 答「用了 HTTPS」——但没说 TLS 版本，也没说是否禁用了旧版本协议。
2. 答「由运维管理」——没有轮换记录，实际上线以来一次没换过。
3. 答「日志都在」——但日志存在同一个应用服务器上，应用管理员可以删。

评审结论是「部分不符合，需整改后复评」。

团队觉得很冤：系统确实加密了、确实有权限控制、确实有日志。但问题在于，**这三件事都只有开发者的口头陈述，没有可被独立核对的凭据。**

## 承诺与证据的分界

一句话区分：

> 承诺说的是「我们会做」，证据说的是「我们做了，这是凭据，你可以自己查」。

| | 承诺书 | 证据 |
| --- | --- | --- |
| 形态 | 一页声明 + 架构图 | 一条可核对的记录 + 复核方法 |
| 谁说的算 | 交付方 | 第三方能独立验证 |
| 时效 | 一次性的 | 持续产生的 |
| 失败时 | 说不清 | 能定位到哪一环断了 |

承诺书不是没用，它是合规材料的封面。但只有封面没有内容，评审一定过不了。

## 证据链的四段

一条完整的证据链，四段缺一不可：

```text
控制项（要求什么）→ 实现（怎么做的）→ 证据（凭据在哪）→ 复核方法（别人怎么验）
```

用上面第 2 个问题举例：

| 段 | 内容 |
| --- | --- |
| **控制项** | 密钥应定期轮换，轮换周期不超过 90 天 |
| **实现** | 使用 KMS 托管密钥，每 60 天自动轮换；应用侧不保存密钥明文 |
| **证据** | KMS 的密钥版本列表（含创建时间）、轮换配置截图、最近三次轮换的操作记录 |
| **复核方法** | 评审方登录 KMS 控制台，查看密钥版本历史；或调 KMS 审计日志接口，按时间范围导出 |

第四段是分水岭。**没有复核方法的证据，仍然只是一份陈述。**

## 六类常见控制项与它们的伪证据

AI 系统交付涉及的合规控制项，集中在六类。每一类都有「看起来是证据但不是」的东西：

| 控制项 | 真证据 | 伪证据 |
| --- | --- | --- |
| **传输加密** | TLS 配置导出（协议版本、套件）、扫描报告 | 「用了 HTTPS」的一句话 |
| **存储加密** | 加密卷配置、密钥 ID、加密算法 | 数据库开启了密码 |
| **访问控制** | 权限矩阵表（角色 × 资源 × 操作）、最近一次权限评审记录 | 系统里有「用户管理」页面 |
| **审计日志** | 日志内容样例、保存位置、保留期限、防篡改机制 | 「日志都留着」 |
| **数据流向** | 数据流向图（含出境/出边界节点）+ 每个节点的处理说明 | 一张系统架构图 |
| **模型与数据来源** | 训练/微调数据来源说明、第三方模型的合规声明 | 「我们用的是合规的模型」 |

第三行（访问控制）有个常见问题：权限矩阵写了，但没人定期评审。评审方常问「上次检查权限是什么时候」，答不上来就说明权限是「设了但没管」——这在审计里等同于没有。

第四行（审计日志）更微妙。日志存在能被删的地方，等于没有防篡改能力。合格的做法是把日志写到独立存储、只追加不修改、或者定期归档到不可变介质。

## 数据流向图是性价比最高的一份

六类里，如果只能做好一份，做数据流向图。

原因：它同时回答了评审方最关心的三个问题——数据从哪来、经过哪里、到哪去。凡是涉及个人信息的系统，这三个问题是必问的。

一份合格的流向图要有：

- **每个节点标注：谁控制、存在哪、保留多久。**
- **跨边界的连线要特别标注**：数据出客户网络、出境内、进入第三方服务，每一处都要单独说明依据。
- **标出「不经过」的路径**：哪些数据确定不会流向哪里。这一条最能体现设计者的清醒。

最后一点常被忽略，但很有用。比如「设备工艺参数不进入外部模型，仅本地检索使用」——这句话本身就是一条证据，它证明你知道边界在哪。

## 证据要能被第三方复核

这是 L2 判据的核心（见 9.4 的「可被反驳」）。

检验方法很直接：**找一个没参与项目的人，给他证据材料，让他独立核对一条控制项。** 他能不能在半小时内得出结论？

做不到，通常是三个原因：

1. 证据是截图。截图不能复核，因为看不到原始状态，也不能验证时间。
2. 证据分散。加密配置在 A 文档、密钥记录在 B 系统、审计日志在 C 目录，没人能把它们串起来。
3. 证据没有版本。三个月后再看，不知道这份配置是不是当前的。

修法：把证据做成「可导出的原始数据 + 一句复核说明」，集中放在一个地方，标注生成时间。

## 证据是持续产生的，不是验收前赶出来的

这一点决定了合规工作的形态。

验收前突击准备材料，只能生产承诺书，生产不了证据——因为证据是系统运行的自然产物：日志、轮换记录、权限评审记录、变更记录。这些东西要么一直在产生，要么根本没有。

所以正确做法是：**在设计阶段就把「产生证据」作为系统的一部分。**

具体到三条：

- 密钥轮换、权限变更、配置修改，都要留下带时间戳的记录，且这些记录本身不可被普通管理员删除。
- 日志的保留期限在部署时就定好（比如 180 天），并在存储配置里落实。
- 每季度做一次权限评审，评审记录归档。

这三条做起来不难，难的是「想到要做」。而想到的时机，只能在需求阶段。

## 一个实际的判断

评审方最不信任的，不是「有缺失」，是「全绿」。

一份写着「全部符合」的材料，专家的第一反应是抽检。抽到一条对不上，整份材料的可信度就崩了。

反过来，一份写着「18 项符合，2 项部分符合（附整改计划）」的材料，反而更容易通过——因为它显示提交方真的逐项检查过。

这与 9.4 讲的验收报告是同一个道理：**诚实列出未达成项，是可信度的来源。**

## 判据卡

| 判据项 | 合格线 | 不合格信号 | 处置 |
| --- | --- | --- | --- |
| 证据链四段完整 | 每条控制项都有实现、证据、复核方法 | 只有承诺与架构图 | 逐条补，先补高风险的 |
| 证据可复核 | 第三方能在 30 分钟内独立核对一条 | 证据只有截图 | 换成可导出的原始数据 |
| 数据流向图 | 标注控制方、存储位置、保留期、跨边界节点 | 只有架构图 | 重画，这是性价比最高的一份 |
| 证据持续产生 | 轮换、变更、评审都有自动记录 | 验收前突击整理 | 改设计，让系统自然产生证据 |
| 日志防篡改 | 日志存于独立位置，应用管理员无法删除 | 日志与应用同机 | 改存储，这一条常被卡 |
| 有未达成项 | 材料里如实列出部分符合项与整改计划 | 声称全部符合 | 如实写，全绿反而引发抽检 |

## 动手练习

**第一题（找漏）**

一个团队提交的合规材料包含：安全承诺书（3 页）、系统架构图、数据流程图、权限设计说明、以及一句「系统已通过内部安全测试」。请指出缺什么，并按优先级排序。

**第二题（取舍）**

客户要求在两周内提交合规材料，但你们的审计日志目前存在应用服务器上，应用管理员可以删除。改造日志存储需要三周。你怎么处理？

## 参考答案

**第一题**

缺的东西按优先级：

1. **可复核的证据本身。** 现有材料全是「说明」，没有一条是「凭据」。最高优先级是补三样：TLS 配置导出、权限矩阵表（含最近评审记录）、审计日志样例（含存储位置与保留期）。
2. **复核方法。** 每条证据配一句「怎么验」。没有这句，证据仍然只是陈述。
3. **「已通过内部安全测试」的支撑材料。** 这句话等于什么都没说——谁测的、测了什么、报告在哪、发现了什么问题。要么补报告，要么删掉这句话。**没有支撑的自证声明，比不写更减分。**
4. **数据来源与模型说明。** 如果涉及第三方模型或训练数据，要有来源说明与合规声明。
5. **未达成项清单。** 现在这份材料隐含「全部符合」，但没有依据。

顺序的理由：先补能被追问的硬证据（1、2），再补容易被忽略的声明类材料（3、4），最后调整整体表述（5）。

**第二题**

不能承诺两周内完成改造，也不能假装日志已合规。三条路：

**路一：如实说明 + 给整改计划（推荐）。**

材料里写：「审计日志当前存储于应用服务器，保留 90 天。已识别风险：应用管理员具备删除权限。整改计划：迁移至独立日志存储，预计三周完成，计划于 X 月 X 日交付。临时措施：已开启日志导出至备份存储，每日一次，备份账号与应用管理员分离。」

这个写法的好处是：它同时展示了「你知道问题在哪」「你有计划」「你有临时缓解」。评审方对这类材料的接受度通常高于「全部符合」。

**路二：先做临时措施，两周内可完成的部分。**

每日导出到独立存储这个动作，一两天能做完。它不能完全解决防篡改（因为导出前仍可删），但它把风险从「完全无保护」降到「有时间窗口」。作为过渡措施是合理的。

**路三：调范围。**

如果这次评审的范围可以分期，把日志防篡改放到第二期。这需要和客户确认评审范围，不是交付方单方面能定的。

**不建议的做法**：写「日志已做防篡改处理」。这句话在两周后如果被抽查，就是一次信任崩塌——而合规材料的价值，全在可信度上。

## 自检清单

- [ ] 每条控制项都有四段：控制项、实现、证据、复核方法
- [ ] 证据是可导出的原始数据，不是截图
- [ ] 有数据流向图，标注了控制方、存储位置、保留期、跨边界节点
- [ ] 证据是系统运行自然产生的，不是验收前赶出来的
- [ ] 审计日志存在应用管理员无法删除的位置
- [ ] 有未达成项清单与整改计划，没有声称全部符合
- [ ] 找过一个未参与者，让他独立核对一条控制项

> 本节为原创论述。
>
> 关于主张的边界：本节讲的是交付物的形态，不是法律意见。具体的合规要求（适用哪套标准、需要哪些控制项、留存多久）必须由客户的法务或专业测评机构确定——交付方的作用是「按给定要求生产可核查的证据」，而不是判断要求本身是否充分。越界替客户解释法规，是另一类风险。
