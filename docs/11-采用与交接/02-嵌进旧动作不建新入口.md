做一个新系统，然后培训用户去用它——这条路失败率极高，因为它要求人改变习惯。而改变习惯的成本，几乎总是被低估。

更省力的做法反过来：**不去动用户的习惯，去动他能拿到新能力的那个位置。**

## 现场

锦程精工的 A 项目，日活掉到 4 之后，团队做了两件事。

第一件是加功能：多轮对话、追问、相关推荐。做完之后日活从 4 涨到 9。

第二件是改形态：不再要求工程师打开一个新系统，而是在**工单填写页的右侧加了一个侧栏**。工程师在写工单的时候，如果不知道故障类型怎么归类，可以在侧栏输入一句现象，侧栏返回建议的类型和依据。点一下，就填进表单。

改完两周，日活不再是一个有意义的概念——因为它不是一个「要去的地方」，而是工单系统里的一个按钮。而侧栏的日均使用次数是 340 次。

对比一下两个方案的成本：

| | 独立系统（第一版） | 嵌入侧栏（第二版） |
| --- | --- | --- |
| 用户要记住 | 有这么个系统，遇到问题去用 | 不用记，写工单时它就在那儿 |
| 一次使用多几步 | 切系统 + 登录 + 输入 + 复制 + 切回 + 粘贴 | 在原地输入 + 点选 |
| 新增账号 | 要 | 不要 |
| 团队要维护 | 一整套前端 | 一个组件 |

功能上，侧栏比独立系统弱得多——它只能回答「故障类型怎么归类」这一类问题，不能做开放式问答。但它被用了 340 次一天，而那个功能完整的系统被用了 4 次。

## 摩擦的三个来源

用户不用一个新东西，通常不是因为不会，是因为**用它比不用它更费劲**。费劲的地方有三处：

**认知摩擦。** 他得先想起来「有这么个东西」。人在工作流里是低能耗模式，遇到问题会走最熟悉的路径——翻手册、打电话、问旁边的人。要让他想到新系统，需要一次额外的认知动作。

**切换摩擦。** 切过去、找到输入框、问、看答案、再切回来。如果宿主系统里有未保存的表单，切换还可能丢数据。这一项最贵，一次切换的实际成本是十几秒到一分钟。

**账号摩擦。** 再来一套账号密码。企业环境里，一个工程师可能有七八个系统的账号，每多一个都是负担。

三个摩擦加起来，就是 10.2 里那个「一次多花四十秒」——而翻手册只要两分钟但不用切。四十秒的差距，足以让人选择那个「更慢但更顺」的路径。

## 三个嵌入层级

嵌入不是一个动作，是三个层次，越深越有效，也越难做：

| 层级 | 做什么 | 例 | 效果 |
| --- | --- | --- | --- |
| **嵌入界面** | 新能力出现在旧界面里 | 工单页侧栏、搜索框旁的建议 | 消除切换摩擦 |
| **嵌入流程** | 新能力成为旧流程的一步 | 填完工单自动提示「同类历史工单」 | 消除认知摩擦 |
| **嵌入数据** | 新能力产出直接进入旧系统 | 建议的故障类型一键填入表单 | 消除复制粘贴 |

第二层和第三层常被混为一谈，区别在于：第二层是「在流程里提醒你」，第三层是「结果直接落进流程」。

第三层最有效，因为它把最后一步的手工动作也省了。锦程精工那个侧栏，如果只是显示一段文字让工程师自己复制，效果会打对折。

## 四个常见的嵌入位置

企业环境里，能嵌入的位置不多，但都很实用：

**工单/表单页。** 这是最典型的位置。用户在这里做判断，最需要辅助。适合嵌「分类建议」「历史相似案例」「参数查询」。

**企业 IM。** 飞书、企微、钉钉里的机器人。优势是用户已经在那儿，不需要新账号。适合嵌「快速查询」「通知与提醒」。
缺点：对话形态不适合复杂交互，长答案在 IM 里读起来很累。

**邮件。** 在收件箱里给一封邮件加「相关历史邮件」的提示。适合客服、销售场景。

**搜索框。** 把原来的关键词搜索扩成「搜索结果 + 一段归纳」。这个位置的优势是用户本来就在搜，零教育成本。

四个位置的共同点：**用户本来就要去那里。** 这是嵌入的本质——不是创造新地方，是占用已有地方。

## 嵌入的代价

嵌入不是免费的，有四个代价要认：

**受宿主限制。** 宿主系统的界面空间、加载性能、权限模型都会限制你。侧栏只能占那么宽，能展示的信息有限。

**升级受制。** 宿主改版，你的嵌件可能要跟着改。宿主的 API 变了，你也得改。

**依赖宿主稳定性。** 宿主的系统挂了，你的能力也就没了。这对可用性设计有影响（见 10.3）。

**责任边界模糊。** 出问题时，是宿主的问题还是嵌件的问题？这需要事先约定，并在界面上能让用户区分。

四个代价加起来，决定了嵌入方案适合「辅助型能力」——它帮用户做判断，但系统本身不是主角。如果新能力需要长时间交互、需要独立的数据视图、需要自己的权限体系，那独立入口更合适。

## 什么时候该建独立入口

不是所有东西都该嵌入。三种情况独立入口更合适：

1. **高频独立使用。** 用户每天专门用半小时的那种（比如数据分析、批量处理），值得有一个自己的地方。
2. **需要深度交互。** 多轮对话、大表格、可视化，这些在侧栏里做不好。
3. **服务的人群本身就是「来用这个」的。** 比如一个给分析师用的工具，分析师的工作就是打开它。

判断依据是一句话：**用户是「顺便用一下」，还是「专门来用它」。** 顺便的嵌入，专门的独立。

## 不要教育用户，改环境

这一节的最后一个判断，也是最重要的一条：

> 当你发现需要写一份使用手册、开一场培训会、发三次推广通知的时候，先停下来想一下——**是不是方案本身有问题。**

培训之所以低效，是因为它试图改变人。而人的习惯是在长期环境里形成的，它背后有合理性：翻手册虽然慢，但结果可信；打电话虽然打扰人，但老师傅的回答带着经验。

新方案要赢，不是靠讲清楚它有多好，是靠**在具体的那个动作上，比老办法更省事**。

锦程精工那个侧栏赢的地方很具体：工程师写工单本来就要填「故障类型」这一栏，而这一栏他经常不确定。侧栏就在这一栏旁边，输入一句现象就能拿到建议。它没有试图让工程师「多用 AI」，它只是让「填这一栏」这件事变容易了。

这也是 1.2 五熵模型里「留存熵」的实质：**留存不靠说服，靠让它成为阻力最小的那条路。**

## 判据卡

| 判据项 | 合格线 | 不合格信号 | 处置 |
| --- | --- | --- | --- |
| 摩擦已量化 | 知道新办法与老办法的单次耗时差 | 只说「新办法更好」 | 实测一次完整流程的耗时 |
| 优先嵌入 | 优先在用户已有的界面/流程里提供能力 | 一上来就做独立前端 | 先做嵌件，验证有人用再做独立入口 |
| 嵌入到数据层 | 结果能直接落进旧系统，不需复制粘贴 | 只展示文字让人自己抄 | 做一键填入 |
| 零新增账号 | 嵌入方案不需要额外登录 | 嵌入了界面但仍要另登一次 | 用宿主的身份体系 |

| 不靠培训 | 方案上线前不需要培训就能用 | 需要开培训会、写使用手册 | 方案有问题，改方案 |

## 动手练习

**第一题（判定）**

下面四个场景，该嵌入还是该建独立入口？说明理由。

1. 给售后工程师的故障诊断助手，他们主要在工单系统里工作。
2. 给数据分析师的报表生成工具，他们每天要生成十几份报表。
3. 给管理层的经营看板，每周看一次。
4. 给客服的「回复建议」，他们在客服系统里逐条处理会话。

**第二题（设计）**

一个团队的 AI 助手已经上线，日活很低。他们发现用户「要查资料时还是习惯翻手册」。请设计一个嵌入方案，并说明你会先做哪一步、怎么验证。

## 参考答案

**第一题**

1. **嵌入。** 工程师的工作流在工单系统里，诊断助手是「顺便用一下」。嵌入工单页的侧栏，输入现象返回可能原因与依据。
2. **独立入口。** 分析师是「专门来用它」的，每天十几份报表意味着高频深度使用，需要完整的界面空间。
3. **嵌入 + 推送。** 每周看一次的东西，最好的形态不是「让他去某个地方看」，是「周一早上自动送到他眼前」——邮件、IM 卡片、或者他已有的管理后台首页。这里的关键不是界面嵌入，是**主动送达**。
4. **嵌入。** 客服在会话界面里逐条处理，回复建议必须出现在那条会话旁边，一键插入。切出去再回来，等于打断服务节奏。

第三题值得注意：它说明「嵌入」不只有空间维度，还有**时机维度**。有些能力的正确嵌入方式是「在对的时候出现」，而不是「在对的地方」。

**第二题**

设计分三步，按摩擦大小排序：

**第一步：找一个具体的动作嵌入，不要做通用入口。**

不要做「在工单系统加一个 AI 搜索框」——那是把独立系统搬进界面，摩擦只是从切换变成了「想起来还有个搜索框」。要做的是找那个「他本来就要翻手册」的具体时刻。

判断方法：跟一天，看他在什么情况下打开手册。锦程精工那个案子里，是「填故障类型不确定」的时候。找到这个时刻，就在那一栏旁边放能力。

**第二步：嵌入到数据层。**

不要只给建议然后让他自己填，做成一键填入。这一步的收益比第一步还大，因为它消除了复制粘贴。

**第三步：验证方式。**

不看日活，看两个数：

- **该动作的使用率**：在触发该动作的工单里，有多少比例用了这个嵌件。
- **该动作的耗时变化**：用了嵌件与没用的，填这一栏平均花多久。

第一个数说明有没有人用，第二个数说明有没有用。两个都涨，才算成功。

验证周期两周。如果使用率低于 20%，不要急着推广，回去看是不是嵌入的位置不对——可能是那一栏不是真正的痛点，也可能是有更顺的老办法（比如他直接问旁边的人）。

最后一条经验：**先做一条流程里的一步，做透，再做第二步。** 一次嵌入五个流程，等于五个都没做好。

## 自检清单

- [ ] 我量化过新办法与老办法的单次耗时
- [ ] 方案优先嵌入用户已有的界面或流程，不是另建入口
- [ ] 结果能直接落进旧系统，不需要用户复制粘贴
- [ ] 不需要新增账号
- [ ] 我评估过宿主的限制、升级依赖与责任边界
- [ ] 上线不需要培训，用户第一次遇到就能用
- [ ] 验证看的是「该动作的使用率」与「耗时变化」，不是日活

> 关于主张的边界：当宿主系统本身老旧、不开放扩展、或者界面已经极度拥挤时，嵌入在工程上可能不可行，这时独立入口是唯一选择。但即便这样，也要尽量降低摩擦——单点登录、深链接（从工单直接跳到带着上下文的问答）、结果回填。**形态可以妥协，摩擦不能不管。**
