一个系统在你走了之后还在被用，可能是惯性；**在你走了之后，客户主动做了一件你没要求过的事**，才是收敛。

这两者的差别，就是留存熵有没有真的降下来。

## 现场

锦程精工的 A 项目，FDE 团队撤场六个月后，做了一次回访。

团队本来只想知道「还在用吗」。信息中心给了一个数字：日活 128，比撤场时的 90 还高。这是一个不错的答案。

但真正让团队意外的是另外三件事：

**第一件，系统被接到了另一条业务线。** 华北区的售后服务组听说华南这边在用，自己找信息中心要了权限，把系统接进了他们的工单流程。这件事没人推动，团队完全不知道。

**第二件，客户自己加了一批文档。** 不是项目组留下的那八本手册，是他们自己整理的三份《区域常见问题汇总》——华北区的工程师根据自己的经验写的，格式还不统一，但确实被加进了知识库。

**第三件，内部有人开始回答问题。** 售后群里有人问「这个系统怎么用」，回答的不是项目组，是华南区那两个最早用的工程师。他们成了内部的「超级用户」。

这三件事，没有一件是合同要求的，也没有一件是团队安排的。

**它们是留存熵收敛的证据。**

## 为什么「还在用」不够

「还在用」这个判断有三个漏洞。

**第一，惯性。** 很多系统在被弃用之前，都会经历一段「还在用」的时期。人们用它，不是因为需要，是因为暂时没有替代品，或者因为「上面要求用」。这种状态可以维持很久，但它随时会崩——通常在某次改版、某个人离职、或者某个更顺手的工具出现时。

**第二，被动。** 用的人和当初被要求用的人是同一批，用法和当初培训的用法一样。这说明系统被固化在流程里，但没有进入人的判断。流程一变，它就掉了。

**第三，不可持续。** 如果每次变更都要找原厂，每次新增内容都要人帮忙，那这个系统实际上还在依赖你。你只是不在现场而已。

三个漏洞的共同特征：**它们都不需要客户做任何主动的事。**

而「主动扩大使用范围」这个动作，恰好同时证明了三件事：

- **有用**：否则不会有人想扩大它。
- **能用**：否则扩大了也用不起来（新业务线的人得自己上手）。
- **想用**：这是最关键的一条，它说明系统提供了别的东西替代不了的价值。

三件事同时成立，留存才算真收敛。

## 三个信号

判断留存熵是否收敛，看三个信号。它们都是可观察的，不需要问客户「你觉得怎么样」。

| 信号 | 具体表现 | 它证明什么 |
| --- | --- | --- |
| **范围扩张** | 被用到新的业务线、新的场景、新的地区 | 价值是可迁移的，不依赖某几个人 |
| **自主维护** | 客户自己更新了知识库、调了配置、修了小问题 | 能力留在了客户那边 |
| **内部传播** | 出现了不依赖你的「超级用户」，在群里回答问题 | 使用不再需要外部推动 |

三个信号里，**第二个是最硬的**。因为范围扩张可能是某位领导推动的，内部传播可能是几个热心人自发的，但「客户自己改了配置还能跑对」，只能说明能力真的转移了。

反过来，如果撤场后第一个月就有人打电话问「系统怎么登录」，那说明 11.3 讲的交接从来没真正做过。

## 留存熵的熵源

五熵模型的最后一层，熵源是什么？

**不是「客户不想用」，是「客户没有能力自己往前走」。**

这个区分很重要。因为这两种情况的解法完全不同：

- 如果是不想用，问题是价值——要么没解决真问题，要么比老办法麻烦。解法在 11.1、11.2。
- 如果是没能力，问题是转移——系统能跑，但客户不知道怎么让它跟着业务变。解法在 11.3。

第三种情况最少被讨论，但它最常见：**系统活着，但停止生长了。**

一个停止生长的系统，会在一年内慢慢失效——因为业务在变，数据在变，用户的问题在变，而它还是交付那天的样子。这时候它不是「被弃用」，而是「被冷落」，两者的结局一样。

## 留存熵是前四层的结果

这是五熵模型里最容易被误解的一点：留存熵不是独立的一层，它是所有层收敛的结果。

| 如果…… | 留存会怎样 |
| --- | --- |
| 意图层没收敛（做错的事） | 上线后没人用，因为解决的不是真问题 |
| 边界层没收敛（范围失控） | 交付了一个庞大的、没人能维护的东西 |
| 现实层没收敛（数据失真） | 答案经常错，用户失去信任 |
| 效果层没收敛（说不清好坏） | 验收过了，但用户心里没底，不敢依赖 |
| 留存层没收敛（能力没转移） | 系统停止生长，一年后自然死亡 |

所以「留存」这一层不能靠最后补。它在前四层就已经被决定了。

反过来说：如果前四层都收敛了，留存通常会自己发生——因为一个解决了真问题、跑得稳、答得准、有明确判据的系统，用户会自己想办法多用它。

**留存不是运营出来的，是前四层的自然结果。** 运营能加速它，但救不了它。

## 一条反向判据

判断留存，还有一个更快的方法：**看你离开后，客户第一个月的行为。**

- 第一个月没人联系你 → 大概率收敛了。
- 第一个月有人问基础操作 → 11.3 的交接没做。
- 第一个月有人问「这个功能能不能加一个 XX」 → 好事。说明他们在用，而且用出了新需求。
- 第一个月有人说「系统挺好，就是没人用」 → 11.1、11.2 没做，价值或摩擦有问题。

第三种情况值得单独说：**客户提新需求，是留存正在发生的信号，而不是范围失控。**

要区分两种情况：一种是「用出来的需求」（他们在真实使用中发现的缺口），一种是「想出来的需求」（没用过但觉得应该有）。前者是好事，后者要警惕（见 4.2 的变更计价）。

区分方法很简单：问他「你们现在是怎么处理这个场景的」。答得出具体做法，说明是真需求；答「就是觉得应该有」，那是想出来的。

## 判据卡

| 判据项 | 合格线 | 不合格信号 | 处置 |
| --- | --- | --- | --- |
| 范围扩张 | 撤场后 6 个月内，被用到至少一个新的场景/业务线 | 只有原班人马在用 | 价值没被验证，回看 11.1 |
| 自主维护 | 客户独立更新过知识库或调过配置 | 每次变更都找原厂 | 交接能力没转移，回看 11.3 |
| 内部传播 | 出现了不依赖你的超级用户 | 所有问题都找你 | 没有形成内部能力，推广全靠外部 |
| 停止生长 | 撤场后没有出现「系统还是交付时那个样子」 | 知识库半年没更新 | 客户没接手维护，预警 |
| 首月行为 | 撤场后第一个月没有基础操作类求助 | 有人问怎么登录、怎么用 | 交接验收没通过 |
| 新需求性质 | 客户提的需求是「用出来的」而非「想出来的」 | 全是想象中的功能 | 用变更计价过滤（4.2） |

## 动手练习

**第一题（判定）**

下面四个场景，撤场六个月后的状态，分别说明留存熵是否收敛？各自的下一步该做什么？

1. 日活稳定，客户自己加了 20 篇文档，但只在一个部门用。
2. 日活增长，被三个部门使用，但每次加文档都找你们。
3. 日活不变，客户从没改过任何配置，也没提过新需求。
4. 日活下降 40%，但客户提了 12 个新功能需求。

**第二题（取舍）**

客户在撤场后第二个月提出：「我们想把系统接到另一个业务线，你们能不能派人支持两个月？」你判断这是留存正在发生，还是范围失控？你怎么回应？

## 参考答案

**第一题**

1. **部分收敛，缺「范围扩张」。** 自主维护这个信号已经有了（加了 20 篇文档），但只在一个部门用，说明价值还没被验证为可迁移。下一步：了解为什么没扩散——是别的部门不知道，还是知道了但不适用。如果是前者，帮他们做一次内部分享；如果是后者，那这个系统的边界就是对的，不必强推。

2. **价值收敛，能力没收敛。** 三个部门在用说明价值成立，但每次加文档都找你们，说明 11.3 的交接只做到了「能运行」，没做到「能维护」。下一步：把知识库的更新流程做成客户能自己操作的形态，陪他们做两次，第三次让他们自己做。

3. **最危险的一种：既没扩散，也没生长。** 日活不变、没有自主维护、没有新需求，说明系统处在「维持」状态——它还在跑，但没有进入客户的判断。这种状态会在某次人员变动或流程调整时突然终结。下一步：不要等，主动去看它在工作流里的位置（11.2），找出摩擦点。

4. **需求旺但价值存疑。** 日活下降 40% 说明实际使用在萎缩，但同时提了 12 个需求——这很可能是「想出来的需求」，不是「用出来的」。下一步：逐个问「你们现在怎么处理这个场景」。答得出具体做法的，是真的；答「觉得应该有」的，先放一放。同时要查日活下降的原因，那个比新需求重要。

**第二题**

判断：**大概率是留存正在发生，但需要设边界。**

理由：客户主动想扩大范围，这是 11.4 讲的第一个信号（范围扩张），而且是客户自己发起的，不是你们推动的。这在留存上是一个非常好的迹象。

但「派两个人支持两个月」这件事，性质不同——它可能变成长期依赖。所以要分两步回应：

**第一步，先弄清新业务线的实际情况。** 问三个问题：

- 新业务线的流程和老业务线差多少？（差得多 = 需要适配，不只是开权限）
- 他们有没有人能接手日常维护？（没有 = 你们要长期驻场）
- 数据能不能共用同一个知识库？（不能 = 要做隔离，工作量另算）

**第二步，按答案给方案。**

- 如果只是「开权限 + 一次培训」 → 免费支持，一周内做完。这类扩张的成本极低，收益极高（新业务线会用出更多真实场景）。
- 如果需要流程适配 → 按变更处理（4.2 的变更计价），做一次小规模交付，交付物包含适配后的配置与更新过的文档。
- 如果需要长期驻场 → 这是运维服务，不是项目支持。按服务计费，且要明确期限与退出条件。

关键是把「支持两个月」翻译成一个有明确范围的事。含糊地答应「我们派人支持」，两个月后会变成「你们怎么撤了」。

最后补一句：这时候最该做的是**让客户的人跟着做**，而不是你们做完交付。范围扩张恰恰是最好的交接机会——新业务线的人本来就要学，学的是「怎么自己配」而不是「怎么用你们配好的」。

## 自检清单

- [ ] 我知道撤场后系统的使用范围有没有扩大
- [ ] 客户独立改过配置或更新过知识库
- [ ] 出现了不依赖我的内部超级用户
- [ ] 撤场后第一个月没有基础操作类求助
- [ ] 客户提的新需求，我能区分「用出来的」和「想出来的」
- [ ] 我知道这个系统现在处在「生长」还是「维持」状态
- [ ] 如果它在维持，我知道摩擦点在哪

> 关于主张的边界：对于一次性交付、明确不打算长期运营的项目（比如某个专项分析工具，用完就归档），留存熵不是必须收敛的——它的生命周期本来就短。这种情况下，判据应该改成「用完之后，客户有没有从中得到可复用的东西」（比如方法、数据集、判断经验），而不是「系统有没有被继续使用」。**不是所有交付都需要长生不老。**
